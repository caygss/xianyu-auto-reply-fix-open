# 商品交付配置异步竞态安全设计

## 背景

商品管理页允许用户为不同商品配置固定链接、导入卡密、自动生成卡密或第三方接口。当前前端使用一个可变的全局 `deliveryConfigContext`，加载商品、保存配置、保存库存、导入和生成卡密之间没有统一的请求所有权。

当用户快速点击商品 A 和商品 B 时，A 的慢响应可能在 B 之后返回，并覆盖 B 的表单、库存或状态。写操作中部分函数还会再次读取全局上下文，可能出现配置写给 A、库存却写给 B 的跨商品串写。

## 目标

- 快速切换商品时，页面只显示最后一次选择的商品。
- 过期响应不得修改上下文、表单、库存、状态文字或按钮忙碌状态。
- 保存、删除、导入、生成和刷新必须始终使用操作开始时捕获的同一商品上下文。
- 写操作期间禁止切换商品，避免用户无法判断正在处理哪个对象。
- 所有等待、成功、失败、取消和部分成功状态使用可行动的中文提示。
- 不改变现有后端接口、数据库结构或交付业务规则。

## 非目标

- 不重写整个 `static/js/app.js`。
- 不引入前端框架、构建工具或第三方状态管理库。
- 不把多商品写操作排队执行。
- 不自动重试写请求。
- 不为读取取消显示错误提示。

## 方案比较

### 方案 A：请求代次、AbortController 与不可变上下文

每次读取产生新的代次和取消信号；写操作捕获冻结上下文，并拥有独立操作令牌。旧请求只能结束自身，不能更新当前界面。

优点：切换立即生效、网络浪费最少、所有权明确、容易测试。缺点：需要抽出一个小型协调器并改造现有调用点。

### 方案 B：串行请求队列

所有商品加载按顺序执行，后续选择等待前序结束。

优点：实现概念简单。缺点：用户需要等待已经不再关心的商品，慢请求会阻塞当前选择。

### 方案 C：只校验响应是否过期

不取消请求，仅在响应返回后比较当前商品。

优点：改动较少。缺点：旧请求继续占用连接，`finally` 和多阶段请求仍容易提前解除忙碌状态。

采用方案 A。

## 架构

### 会话协调器

新增独立文件 `static/js/delivery-config-session.js`，使用无依赖的 UMD 风格导出，浏览器通过全局对象使用，Node 测试通过 `module.exports` 使用。

协调器只管理所有权，不读写 DOM，也不发起网络请求：

- `loadGeneration`：单调递增的读取代次。
- `loadAbortController`：当前读取的取消控制器。
- `activeContext`：当前已完整解析并冻结的商品上下文。
- `writeOperation`：当前写操作令牌和冻结上下文。

协调器提供以下能力：

- 开始读取时取消旧读取并返回 `{ generation, signal, selection, isCurrent() }`。
- 只有当前读取可以提交包含 `accountId`、`itemId`、`itemTitle`、`cardId` 的冻结上下文。
- 只有当前读取可以结束自己的加载状态。
- 写操作开始时复制并冻结当前上下文，生成唯一令牌。
- 只有令牌所有者可以结束写操作。
- 写操作存在时拒绝新的商品读取。

上下文不包含令牌、卡密、接口密钥或其他敏感内容。

### UI 集成层

`static/js/app.js` 保留表单构建和渲染职责，但不得直接依赖可变全局上下文完成异步操作。

- `openDeliveryConfigForItem` 开始新读取后立即清空旧表单、旧库存和旧预览。
- `deliveryConfigFetch` 和 `deliveryConfigFetchOptional` 接受并传递 `signal`。
- 每个 `await` 后都检查读取是否仍为当前代次。
- `saveInventorySettings`、`refreshDeliveryInventory` 等内部函数必须接收显式上下文，禁止在内部再次调用 `requireDeliveryConfigContext()`。
- 保存、删除、导入、生成和继续处理在开始时捕获一次写操作对象，后续路径全部使用其中的冻结上下文。
- 状态更新和忙碌状态释放必须校验读取代次或写操作令牌。

### 页面结构

在“当前商品专属配置”标题下持续显示：

- 闲鱼账号 ID。
- 商品标题。
- 商品 ID。

未选择商品时显示“请先从商品列表点击‘设置交付方式’”。加载失败时保留被选择商品的身份，但不建立可写上下文。

商品列表中的“设置交付方式”按钮在写操作期间全部禁用；加载期间保持可用，以便用户立即切换商品。

## 数据流

### 读取商品配置

1. 用户点击商品 A。
2. 协调器取消旧读取，生成 A 的读取代次。
3. 页面清空旧表单和库存，显示 A 的身份及“正在加载商品 A”。
4. 创建或解析 A 的 delivery card。
5. 若 A 已过期，停止处理，不显示错误。
6. 提交 A 的冻结上下文。
7. 使用同一取消信号并行读取配置、库存设置、库存摘要和脱敏预览。
8. 所有结果齐全且 A 仍为当前读取时，一次性渲染。
9. 只有 A 的读取所有者可以解除加载状态。

若用户在第 4 至第 8 步点击 B，A 被取消并静默结束，B 从第 2 步重新开始。A 的任何 `catch` 或 `finally` 都不能修改 B。

### 写入商品配置

1. 用户点击保存、删除、导入、生成或继续处理。
2. 协调器复制并冻结当前上下文，生成写操作令牌。
3. 禁用交付配置写按钮和所有商品切换按钮。
4. 状态文字明确显示正在处理的商品。
5. 所有请求路径只使用写操作中的上下文。
6. 只有写操作令牌所有者可以显示最终状态并重新启用按钮。

写操作期间不会开始新的商品读取。用户点击禁用按钮不会产生请求。

### 配置与库存的部分成功

卡密模式保存包含两个后端请求：先保存交付方式，再保存库存设置。这两个请求无法形成跨接口事务，因此必须明确处理部分成功：

- 两个请求均成功：显示“商品 A 的交付配置和库存设置已保存”。
- 第一个请求失败：保留表单，显示保存失败原因，不执行第二个请求。
- 第一个成功、第二个失败：显示“商品 A 的交付方式已保存，但库存设置保存失败，请再次保存”。

页面不得把部分成功显示成全部成功，也不自动回滚已成功的交付配置。

## 错误与取消

- `AbortError` 表示用户切换商品，不显示错误、Toast 或内部异常名。
- 当前读取失败时保留所选商品身份，清空旧数据，禁用写按钮，并提示用户重新点击该商品的“设置交付方式”。
- 写入失败时保留用户输入，重新启用按钮，并在提示中包含商品标题和下一步。
- 过期读取的成功、失败和 `finally` 全部静默丢弃。
- 页面离开商品管理区或重新初始化时取消当前读取，并清除未提交上下文。
- 错误提示不得包含请求代次、AbortController、堆栈、内部 URL、令牌或密钥。

## 可访问性与视觉状态

- 沿用 `DESIGN.md` 的“手把手操作台”规则。
- 所有主要按钮最小高度为 44px，并具备可见键盘焦点。
- 配置面板加载时设置 `aria-busy="true"`。
- 状态文字使用现有 `aria-live` 区域，并同时使用文字和语义色。
- 禁用按钮保持标签可读；提示解释为什么当前不能切换商品。
- 取消旧读取不触发闪烁、错误动画或无意义 Toast。

## 测试设计

### 纯协调器测试

使用 Node 内置 `node:test`，不引入 npm 依赖：

- B 开始后 A 的 `isCurrent()` 为 false，A 的 signal 已取消。
- 只有当前读取可以提交上下文。
- 提交的上下文不可变。
- 只有读取所有者可以结束加载。
- 写操作捕获上下文后，全局选择变化不会改变写操作目标。
- 写操作期间拒绝新读取。
- stale 写令牌不能解除当前写状态。

### UI 集成测试

使用最小 DOM/fetch 测试夹具执行真实前端函数：

- A 慢、B 快时只渲染 B，A 的返回和 `finally` 无副作用。
- A 被取消时不显示“打开失败”。
- B 加载失败时旧表单被清空、写按钮禁用、提示可行动。
- 保存 A 时所有请求 URL 均属于 A；尝试切换 B 不发起读取。
- 卡密模式的配置和库存请求使用同一冻结上下文。
- 配置成功、库存失败时显示部分成功，不显示全部成功。
- 删除、导入、生成和库存刷新均不重新读取全局上下文。
- stale 操作不能更新状态或启用按钮。
- 重新渲染商品列表时，新生成的切换按钮继承当前写忙碌状态。

Node 测试通过一个 pytest 包装测试纳入全量 `pytest`，确保 Windows 分发前不会被遗漏。

### 手动验收

- 在浏览器中快速依次点击至少三个商品，最终面板只显示最后一个商品。
- 使用网络延迟模拟 A 慢 B 快，确认无旧数据闪回。
- 保存卡密配置期间确认商品切换按钮禁用，完成后恢复。
- 在浅色、暗色、520px 和 900px 宽度下检查身份信息、加载提示和按钮状态。
- 仅使用键盘完成选择商品、保存和错误恢复流程。

## 验收标准

- 不存在可复现的 A/B 表单、库存、状态或写入串线。
- 旧请求不会覆盖新请求，也不会提前解除新请求的忙碌状态。
- 所有写操作以开始时的冻结上下文为唯一目标。
- 写操作期间商品切换请求为零。
- 读取取消对用户静默，真实失败提供中文原因和下一步。
- 新测试进入全量 pytest，现有 delivery、inventory 和商品管理测试无回归。
