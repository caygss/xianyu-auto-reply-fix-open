# 闲鱼自动发货傻瓜式引导与多渠道交付设计

日期：2026-07-29  
状态：已获用户批准，等待文档 review  
适用版本：Windows 单机分发包

## 1. 目标

把首次登录、闲鱼账号连接、人工验证、商品交付配置、自动发货和原商品重新上架整合成一条中文向导流程。

目标用户不需要理解 WebSocket、Token、鉴权、退避等技术概念，只需要按照页面显示的“当前状态、是否需要操作、下一步按钮”完成配置。

向导必须同时覆盖两种主要商品交付方式：

- 网盘固定链接；
- 卡密。

卡密支持三种来源：

- 文本或 TXT/CSV 文件导入；
- 第三方发卡平台 API；
- 项目内随机卡密生成。

项目只负责卡密的保存、库存管理、锁定和发货，不负责卡密兑换、验证或判断第三方卡密是否真实有效。自动生成的卡密只是交付文本，买家或商家需要自行提供后续兑换/验证系统。

## 2. 非目标

本次设计不包含：

- 开发卡密兑换网站；
- 验证第三方卡密有效性；
- 代替闲鱼执行平台强制的风控冷却；
- 为多个用户共享同一运行实例；
- 引入 Docker 或云端中心数据库；
- 改变原项目 AGPL-3.0 开源和分发边界。

## 3. 用户体验总流程

首次打开程序后，默认进入“开通闲鱼自动发货”向导。页面显示当前步骤和总进度，例如“第 2 步，共 6 步”。

### 3.1 登录程序

首次登录使用默认账号后，提示用户立即修改密码。修改完成后才能继续向导。

### 3.2 扫码绑定闲鱼账号

页面明确提示使用闲鱼 App 扫码。扫码成功后自动进入连接步骤，不要求用户再次点击无意义的刷新按钮。

### 3.3 建立连接与等待

用户看到的是：

> 扫码成功，正在建立闲鱼连接。预计还需 X 分钟，当前无需操作，请不要关闭程序。

项目自身可控的扫码稳定等待默认压缩为 5 分钟，并显示实时倒计时。闲鱼已经下发的强制风控冷却不强行取消，页面必须显示明确原因、剩余时间和下一次可操作时间。

刷新网页不会重置流程或重新扫码。

### 3.4 人工验证

第一次检测到滑块、验证码、人脸或其他必须人工完成的验证时：

1. 停止同一问题的自动重复尝试；
2. 打开可见浏览器窗口；
3. 在向导中提示用户完成验证；
4. 用户点击“我已完成验证”；
5. 系统立即重新检查账号状态。

如果浏览器没有打开，显示“重新打开验证页面”。如果验证失败，立即说明失败，不让用户盲等到退避结束后才知道。

### 3.5 确认账号可用

系统自动检查：

- 账号实例正在运行；
- 闲鱼连接已建立；
- Session 可用；
- Token 可用；
- 商品接口可同步；
- 实时消息链路可用。

全部通过后显示“账号已连接，可以开始配置自动发货”。

### 3.6 配置商品交付

在同一个向导中完成默认交付方式和商品专属交付方式配置。

商品交付配置同时常驻在商品管理页面。首次显示时用户可以点击“×”关闭提示，也可以点击缩放按钮收起/展开；关闭提示不会删除配置，用户可以随时通过“商品交付配置”按钮重新打开。

### 3.7 配置自动发货与重新上架

向导提供：

- 自动发货开关；
- 测试模式；
- 原商品售出后的自动重新上架开关；
- 发布/重新上架前的配置检查。

### 3.8 最终检查

向导显示清单：

- 账号连接：通过；
- 商品交付配置：通过；
- 自动发货：已开启；
- 自动重新上架：已开启或按用户选择；
- 当前可以等待买家下单。

后续如果账号断开或需要验证，系统回到对应步骤，不要求用户重新学习整个流程。

## 4. 用户可见状态设计

内部状态必须转换为中文用户提示，技术详情默认折叠。

| 系统情况 | 用户看到的提示 | 主操作 |
|---|---|---|
| 等待扫码 | 请打开闲鱼 App 扫码 | 扫码 |
| 扫码成功 | 扫码成功，正在连接闲鱼 | 无需操作 |
| 项目稳定等待 | 正在保护账号，预计还需 X 分钟 | 等待 |
| 需要人工验证 | 请在新打开的浏览器中完成验证 | 我已完成验证 |
| 浏览器未打开 | 验证页面启动失败 | 重新打开验证页面 |
| 验证失败 | 验证没有通过，请重新操作 | 重新验证 |
| 平台强制冷却 | 闲鱼暂时限制登录恢复，预计 X 分钟后可重试 | 等待 |
| 连接成功 | 账号已连接，可以开始配置 | 下一步 |
| 缺少商品配置 | 还差 1 项：请填写默认交付内容 | 去配置 |
| 配置格式错误 | 内容格式不正确，请检查后重试 | 修改配置 |
| 库存不足 | 卡密库存不足，还需要 X 个 | 去补充库存 |
| 全部完成 | 自动发货已准备好 | 完成 |

不再向普通用户直接显示“重连中”“登录恢复退避中，暂不可接管”等内部术语。原始状态、错误堆栈和触发原因放在“查看技术详情”中。

每个状态最多显示一个主操作按钮。等待状态必须明确写出“当前无需操作”。

## 5. 多渠道交付模型

### 5.1 交付方式

每个商品选择一种交付方式：

- 网盘固定链接；
- 本地卡密库存；
- 项目自动生成卡密；
- 第三方发卡平台 API。

默认配置适用于所有未设置商品专属配置的商品。商品专属配置优先于默认配置。

### 5.2 网盘固定链接

保存完整链接和可选说明文本。配置检查只验证内容非空、格式合理和商品确实绑定了交付内容，不声称验证网盘权限或文件可下载性。

### 5.3 卡密导入

支持逐条粘贴和 TXT/CSV 批量导入。导入时自动去重，显示新增数量、重复数量和无效空行数量。

### 5.4 第三方发卡平台

通过适配器抽象第三方 API。配置包括平台地址、认证信息、商品映射和请求参数。订单发货时一次请求购买数量；返回数量不足时不确认发货，保留订单待处理。

### 5.5 项目内自动生成卡密

项目生成唯一的随机文本卡密，可配置数量、前缀、长度、字符集和批次。支持 TXT/CSV 导出。

项目不提供卡密兑换和有效性验证。页面必须明确说明生成的卡密只是交付文本。

## 6. 库存和数量规则

### 6.1 库存概念

区分以下字段：

- 库存上限：用户允许的最大可用卡密数量，例如 100；
- 当前可用库存：尚未锁定、尚未发出的卡密数量；
- 已锁定库存：正在处理订单占用的卡密数量；
- 已发出数量：历史发货记录中的卡密数量。

库存上限不是累计生成总量。

### 6.2 推荐自动生成策略

采用“预生成库存 + 低库存自动补充到上限”：

- 启用后先生成至库存上限；
- 成功发出 1 个卡密，当前可用库存减 1；
- 库存降到预警线时，后台提前补充；
- 补充目标为库存上限；
- 补充过程不阻塞买家订单；
- 单次生成数量受上限约束，避免误生成过多。

默认库存上限为 100，低库存预警线为 20；用户可以修改。

对于导入卡密，库存只能通过导入补充。对于第三方 API，库存以平台返回或平台查询结果为准；项目内自动生成策略不适用于第三方真实授权码。

### 6.3 按购买数量发货

需要发出的卡密数量等于买家购买数量。

系统必须先检查并一次性锁定全部数量：

- 数量足够：锁定 N 个，组合成一条发货内容；
- 数量不足：整单暂停，不部分发货，并提示还需要 X 个；
- 用户补充库存后：点击“继续处理”，系统使用原订单重新尝试；
- 同一订单重试：读取原发货记录或原锁定记录，不创建重复发货。

### 6.4 库存事务

- 发货成功后统一扣减并标记为已发出；
- 发货失败释放锁定卡密；
- 订单重复通知不得再次占用新卡密；
- 进程重启后可从数据库恢复锁定和发货状态；
- 每张卡密有唯一标识和生命周期状态。

## 7. 等待、重试和人工介入策略

### 7.1 可控等待

缩短项目自身的无意义等待，包括：

- 连接状态轮询间隔；
- 验证完成后的检查间隔；
- 重连前的短暂等待；
- 页面刷新后的状态更新间隔。

### 7.2 不可控等待

闲鱼已明确触发的风控冷却不能承诺强行取消。系统必须：

- 返回动态剩余秒数；
- 页面实时递减；
- 说明触发原因；
- 明确下一次可操作时间；
- 冷却结束后自动继续检查。

### 7.3 首次人工验证优先

第一次检测到需要人工处理时立即停止自动重复尝试，并打开可见浏览器。只有平台明确要求冷却时才进入等待。这样避免用户等待很久后才发现自动滑块失败。

## 8. 组件和数据边界

### 8.1 向导状态

向导需要有明确的后端状态对象，至少包含：

- 当前步骤；
- 用户可见标题和说明；
- 是否需要用户操作；
- 主操作类型；
- 剩余时间和截止时间；
- 下一步可执行条件；
- 技术状态和错误详情。

前端只负责展示和发起用户操作，不通过猜测字符串决定复杂业务状态。

### 8.2 交付适配器

统一交付接口：检查配置、检查库存、锁定内容、提交发货、确认成功、释放锁定。网盘、卡密库存、自动生成和第三方 API 各自实现适配器。

### 8.3 本地隔离

继续遵循一台电脑一个用户一个安装目录。账号数据、卡密库存、订单记录、浏览器配置和日志都保存在该安装目录的本地数据边界内，不做跨安装共享。

## 9. 验收标准

以下场景必须通过：

1. 新用户只按页面提示完成默认登录和扫码；
2. 扫码后能看到明确倒计时和“当前无需操作”；
3. 首次滑块失败不会静默重试多轮，能打开可见浏览器并指导用户；
4. 退避剩余时间在刷新页面后仍然正确，并持续递减；
5. 网盘链接可作为默认交付内容，并可被单个商品覆盖；
6. 卡密可粘贴、导入、导出和查看库存；
7. 自动生成卡密只生成到上限，发出后库存递减；
8. 同一订单购买数量为 N 时发出 N 个不同卡密；
9. 库存不足时整单暂停，不部分发货；
10. 发货重试不会重复扣库存或重复发卡；
11. 第三方 API 返回数量不足时整单暂停；
12. 商品交付配置提示可关闭、缩放并重新打开；
13. 自动发货和原商品重新上架都能在向导中配置并完成检查；
14. 用户最终能看到“账号和自动发货已准备好”；
15. 所有技术错误都有普通用户提示和可展开的技术详情。
